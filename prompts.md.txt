# レポートAI プロンプト集

このファイルは検証用プロンプトのバージョン管理。
Claude は依頼時に該当 version を読み、プレースホルダーを以下の規則で埋めて生成する。

---

## プレースホルダー埋め方

| プレースホルダー | 埋める値 | 参照元 |
|---|---|---|
| `{master_fmt}` | 新FMT本文 | `新FMT.md` |
| `{client_name}` | 会社名 | `[会社名]_情報.md` |
| `{client_area}` | エリア | `[会社名]_情報.md` |
| `{client_auto_memo}` | 特徴メモ | `[会社名]_情報.md` |
| `{diff_text}` | 当月の構造化数値 | `[会社名]_[年月]_数値.xlsx` |
| `{detail_text}` | 詳細データ | `[会社名]_[年月]_数値.xlsx` |
| `{knowledge_text}` | **直前1ヶ月** の正解レポート | `[会社名]_[直前月]_正解.{md\|pdf}` |
| `{operator_memo}` | 担当者メモ | `[会社名]_[年月]_メモ.md` |
| `{previous_sections}` | 同じ依頼内で既に生成済みのセクション | チャット文脈 |

### `{knowledge_text}` の補足
- 例：`アルネット 2025-03` 生成時 → `アルネット_2025-02_正解.pdf`（または `.md`）を入れる
- 直前月の正解がナレッジに無ければ「（参照可能な過去レポートなし）」と記載

### `{operator_memo}` の補足
- `[会社名]_[年月]_メモ.md` がナレッジに無ければ「（特記事項なし）」と記載

### `{diff_text}` / `{detail_text}` の補足
- Excelファイルの内容を Claude が解釈して埋める
- 本番アプリの `buildPrompt` のパース結果と完全一致しない可能性があるが、検証目的（プロンプト文言の磨き）には影響しない前提で進める

### 厳守事項
- **検証対象月の正解レポート（例：3月生成時の3月正解）は絶対に参照しない**（カンニング防止）
- 必要なファイルがナレッジにない場合は、生成前に川嶋に確認すること

## v1（初期版）

4セクション共通の構造。最後の指示文のみセクションごとに変わる。

### 共通プロンプト本体

```
[Layer 1] マスターFMT
{master_fmt}

[Layer 2] クライアント属性
会社名: {client_name}
エリア: {client_area}
特徴メモ: {client_auto_memo}

[Layer 3] 今月の構造化数値
{diff_text}

[Layer 3-b] 詳細データ
{detail_text}

[Layer 4] 過去レポート参照（文体・施策の参考）
※ マスターFMTと矛盾する場合はマスターFMTを優先すること
{knowledge_text}

[Layer 5] 担当者メモ
{operator_memo}

[既に生成済みのセクション（文脈として参照）]
{previous_sections}

---
```

### セクション別の最終指示

| セクション | 最終指示文 |
|---|---|
| サマリー | 上記をもとに「サマリー」セクションのみを生成してください。Markdown形式で出力すること |
| フォロワー分析 | 上記をもとに「フォロワー分析」セクションのみを生成してください。Markdown形式で出力すること |
| リーチ分析 | 上記をもとに「リーチ分析」セクションの **フィード部分のみ** を生成してください。Markdown形式で出力すること |
| アカウント分析 | 上記をもとに「アカウント分析」セクションのみを生成してください。Markdown形式で出力すること |

## バージョン追加ルール

新version追加時は以下を記載：

- **version 番号**：v2, v2.1 など
- **変更箇所**：共通プロンプト本体 / セクション別指示 / プレースホルダー定義 のどれを変えたか
- **変更意図**：前versionで何が問題で、何を改善しようとしたか
- **追加日**

例：

```
## v1.1（2026-XX-XX）

変更箇所: フォロワー分析の最終指示
変更意図: v1 では「Goodの理由」が抽象的すぎたため、具体的な投稿要素まで踏み込ませる指示を追加
変更内容:
[差分を記載]
```

## v1.2（2026-05-07）

変更箇所: マスターFMT（`新FMT.md`）

変更意図: v1.1 でフォロワー分析を生成した際、以下3点が頻出した

- 推定・観察形の文末（「〜と見られる」「〜が見られる」「〜といえる」）

変更内容: 新FMT.md

- 表記ルール
    - 「運用者本人が書く月次報告書である前提」を明記
    - 文末表現を OK/NG リスト化（「〜と考察」は OK のまま広く許容）
- 考察の品質基準
    - 自己評価コメントNGを追加
    - NG/OK 例を3組追加（「絶対値として高い実績」NG、受け身構造NG など）

共通プロンプト本体・セクション別最終指示は v1 と同じ

## v1.3（2026-05-07）

変更箇所: マスターFMT（`新FMT.md`）

変更意図: v1.2 でフォロワー分析を生成した際、以下3点が頻出した

- 単月の数値変化を「当月施策の単月効果」として因果づける
    - 例：「女性25-34が81人 → 自然流入が発生」（実際は1月以降継続のフォロー施策の累積結果）
- 性別・年代の構成を「狙って獲得した結果」として書く
    - 例：「ターゲット世代を抑えたフォロー施策」「45-54男性を確保」
    - 実際のフォロー施策は商圏（エリア・ジャンル）までしか絞り込めず、性別・年代の細かいコントロールは不可能
- Good/Bad項目の粒度が揃わず、上位の論点と重複した派生数値を独立項目として立てる
    - 例：「重点世代計561人」を立てた直後に「女性25-34が81人」を別Goodにする

これらは「フォロー施策のコントロール粒度」「単月数値と継続運用の関係」「Good/Bad項目の独立性」がマスターFMTに明文化されていないことに起因する。

変更内容: 新FMT.md

- 考察してはいけないこと > フォロワー分析
    - 「性別・年代の構成を施策の直接結果として因果づけない」を追加
    - 「単月の数値変化を当月施策の単月効果として書かない」を追加
- 考察の品質基準
    - 「Good/Bad項目は独立した論点にする」を追加
    - NG/OK 例を1組追加（重複した派生数値を別項目に立てるNG）

共通プロンプト本体・セクション別最終指示は v1 と同じ

## v1.4（2026-05-07）

変更箇所: マスターFMT（`新FMT.md`）／ 検証フロー（`概要.md`）

変更意図: v1.3 でリーチ分析（フィード）を生成した際、以下2点が課題として顕在化

- 「フィード・リール各代表する投稿の個別考察を含む」の解釈が曖昧で、TOP/Worst の両方を出力していた
    - 新FMT本来の意図は代表投稿1つ
- 「当月の施策」セクションを、先月正解レポートの「次月の対策」から意味は同じだが用語を翻案して書いていた
    - 例：先月「素材をアップで映した画像」→ 当月「アップショット」と要約
    - 運用者本人が書く月次報告書の前提に立つと、月をまたいだ用語の連続性が失われ不自然

加えて、検証フローの整理として、リーチ分析時はTOP投稿のスクショが個別考察に必要だが、川嶋側でTOP投稿を毎回特定するコストが大きいため、依頼を受けた Claude が数値からTOP候補を出して川嶋がスクショを送る運用に変更。これは検証フローの変更なので `概要.md` に記載。

変更内容:

- 新FMT.md
    - レポート構成（現行）
        - 「フィード、リール各代表する投稿の個別考察を含む」を「フィード・リール各1投稿の個別考察を含む（TOP投稿のみ）」に変更
    - 「過去レポートからの引き継ぎ」セクションを新設
        - 「当月の施策」は先月正解の「次月の対策」を原文用語のまま転記
        - Good/Bad考察・代表投稿の個別考察・次月対策はゼロベース
- 概要.md
    - 検証の進め方に「リーチ分析時のTOP先行特定フロー」を追記
    - 検証フローが本プロジェクト内限定（本番アプリでは依頼時にスクショ全添付）である旨も注記

共通プロンプト本体・セクション別最終指示は v1 と同じ

## v1.5（2026-05-07）

変更箇所: マスターFMT（`新FMT.md`）／ 検証フロー（`概要.md`）

変更意図: v1.4 でリーチ分析（フィード）を生成した際、以下3点が課題として顕在化

- 個別投稿スクショ・数値から確認できない範囲の推測を書いていた
    - 例：「全投稿で素材アップカットを徹底」「当月のフィードはナチュラル・白基調の表紙が大半」
    - グリッド全体の傾向はプロフィールグリッドのスクショがないと本来書けない
- AI側が、運用者の観察に基づかない外部要因を「言い訳」として勝手に持ち出していた
    - 例：「月末投稿による後伸び未反映が一因」
    - ただし外部要因そのものを禁止すると、運用者本人が観察した正当な要因（アルゴリズム変動による全社的な数値低下など）まで書けなくなる
    - そのため「**根拠の所在**」をルール化し、`operator_memo` 経由で運用者の所感として入った要因のみ反映可能とする
- Good/Bad の項目数が4個以上に膨らみがちで、各論点の重みが希薄化していた

これらをマスターFMT側で明文化することで、リーチ分析だけでなく他セクションでも同種の推測・冗長化を予防する。
加えて、グリッド全体の考察を可能にするための運用フローを `概要.md` 側に追記する。

変更内容:

- 新FMT.md
    - 考察の品質基準
        - 「Good/Bad項目は各2〜3個を上限とする」を追加
    - 考察してはいけないこと > リーチ分析（新設）
        - 「個別投稿スクショ・数値から確認できない範囲の推測をしない」を追加
            - 例外：プロフィールグリッドのスクショが依頼時に添付されている場合は、その範囲で観察可能な傾向として記述してよい
        - 「運用者の所感（`operator_memo`）に記載のない外部要因・運用都合を、要因として持ち出さない」を追加
            - 判断基準：要因として書く前に「数値データ」「投稿スクショ」「`operator_memo`」のいずれかに根拠があるかを確認、3つに根拠がない場合は書かない
- 概要.md
    - 検証の進め方
        - リーチ分析時のフローに「グリッド全体の傾向を考察に含めたい場合は、プロフィールグリッドスクショも合わせて依頼する」を追記
    - TODO（将来実装）セクションを新設
        - `operator_memo` 入力UIの実装計画を明文化
        - 本番アプリで運用者所感の入力欄を実装し、外部要因を運用者本人の観察として記入できる経路を確保する旨を記載

共通プロンプト本体・セクション別最終指示は v1 と同じ

## v1.6（2026-05-07）

変更箇所: マスターFMT（`新FMT.md`）／ 検証フロー（`概要.md`）

変更意図: v1.5 で家計画3月のアカウント分析を生成した際、特定ストーリー（「理想のリノベーションを叶えます✨」など）がリンククリックを牽引したと因果づけて書いていた。しかし手元にあったのは日次の WEB リンククリック総数のみで、ストーリー単位の内訳は数値データに含まれない（運用者がアカウントログインして手動取得する数値のため）。スクショも添付されていない状態で個別ストーリーに帰属させるのは、リーチ分析側で v1.5 で禁止した「個別投稿スクショ・数値から確認できない範囲の推測」と同じ構造の踏み外し。

加えて、本番アプリ側でストーリーズリンククリック数の手動入力欄と、ストーリースクショアップロード欄を実装しないと、根拠ベースのアカウント分析考察が成立しない構造であることが判明したため、TODO に明文化する。

変更内容:

- 新FMT.md
    - 考察してはいけないこと > アカウント分析（新設）
        - 「ストーリー単位の因果づけをしない」を追加
            - 例外：ストーリー単位のリンククリック内訳（`operator_memo` または手動入力欄経由）またはストーリースクショが提供されている場合のみ可
            - データなしの場合は集計レベル（プロフアクセス計 / WEBリンククリック計 / ストーリーリンククリック総数）に留める
        - 「ストーリーの文言・デザインの効果に踏み込まない」を追加
            - スクショ・内訳がない限り「『理想』訴求が機能した」のような効果の因果づけはしない
        - 「ハイライトの効果は当月新設・改修した場合に限り集計レベルでの寄与可能性として書ける」を追加
        - 各項目に NG/OK 例を併記
- 概要.md
    - 検証の進め方
        - アカウント分析依頼時のストーリーデータ取得フローを1行追記
    - TODO（将来実装）

        - 検証フローでの代替手段（依頼受領時に運用者へ取得を依頼）も併記
